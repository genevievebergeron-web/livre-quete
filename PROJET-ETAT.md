> **v2.5.0 (25 juillet, poussé, session nocturne autonome) — Correctif 1 : reset hebdomadaire des pièces + `coinsLifetime`.** Premier item du chantier approuvé par Gen le 24 juillet au soir (voir `~/.claude/plans/le-design-de-mon-mighty-mountain.md`, section « Chantier approuvé »). **Reset** : `migrateGameState` (`App.jsx`) compare `gs.coinsWeek.week` à `custodyWeekKey()` (vendredi-ancre, PAS `weekKey()` qui est lundi) à chaque chargement — si différent, `coins` repasse à 0. **Premier déploiement sans casse** : si `coinsWeek` est absent (jamais encore vu ce code), AUCUN reset n'a lieu — seul un `coinsWeek` est semé silencieusement, le solde actuel des 4 enfants reste intact jusqu'au prochain vrai changement de semaine. **`coinsLifetime`** : nouveau champ jamais réinitialisé ni décrémenté, seedé depuis `coins` actuel au premier déploiement, incrémenté à CHAQUE gain de pièces confirmé comme un vrai gain (validation de tâche par le parent, complétion forcée, bonus mini-jeu, victoire de boss ×3 chemins de code, objectif du jour) — fusionné entre appareils par `Math.max` dans `mergeGS` (même patron que `xp`, sûr car monotone). Entrée CHANGELOG in-app ajoutée pour prévenir les enfants avant le premier reset réel.
> **Décision de conception ouverte, documentée plutôt que forcée** : les 2 outils manuels du portail parent qui touchent aux pièces — `handleAdjustXP` (bonus XP+pièces) et `handleAdjustCoins` (ajustement direct, dont son propre commentaire de code cite « ex: rembourser une récompense ») — ne touchent PAS `coinsLifetime` dans cette passe. Raison : `handleAdjustCoins` sert à la fois de remboursement manuel (ne devrait PAS re-compter dans le total à vie, déjà compté à l'origine) et de bonus manuel (devrait compter) — la fonction ne distingue pas les deux cas, et deviner créerait soit un double-compte soit un badge manqué. Choix fait : aucun des deux ne compte, cohérence entre les deux outils plutôt qu'une hypothèse arbitraire sur l'usage réel. Si Gen confirme qu'elle utilise ces boutons uniquement pour de vrais bonus (jamais des remboursements), on pourra les faire compter dans une passe future. Idem pour les annulations (`handleDeComplete`/undo) : `coinsLifetime` n'est jamais décrémenté même quand elles retirent des pièces, par cohérence stricte avec « jamais décrémenté » demandé par Gen.

> **v2.3.0 (24 juillet, poussé) — Lot 6 #26 fini : migration couleurs des enfants + 2 bugs de superposition + `.btn-press` partout.** Gen a testé le site en direct après v2.2.0 et signalé 3 problèmes concrets :
>
> **1) « L'écran d'accueil est toujours fluo »** — trouvaille importante : la couleur de chaque enfant (`player.color`) est choisie une fois dans `SetupWizard` et **enregistrée telle quelle** dans son profil — elle ne se recalcule jamais depuis la palette `COLORS` à chaque rendu. Désaturer `COLORS` dans le code (fait en v2.2.0) n'avait donc aucun effet sur les enfants déjà configurés, seulement sur un enfant qu'on créerait après coup. Corrigé par une migration ponctuelle (même patron que `rotativeCleanupV1`) : `COLOR_DESATURATE_MAP` (ancien hex → nouveau hex pour les 9 couleurs vives de l'ancienne palette) appliquée une fois à `config.players[].color` au chargement, `colorToneDownV1` posé pour ne jamais re-transformer une couleur déjà migrée. Palette `COLORS` elle-même complétée : les 8 couleurs qui n'étaient pas dans les 7 couleurs "core" de v2.2.0 (bleu, magenta, orange-rouge, teal, violet, rose) désaturées aussi. **Vérifié en Chrome** : joueur test avec une couleur `#FFD700` (valeur originale de la palette) + flag de migration effacé → rechargement → couleur devenue `#D9BC5C` automatiquement, flag reposé.
>
> **2) « Le menu du bas passe derrière les contrôles du téléphone »** — la barre d'onglets fixe (`position:fixed,bottom:0`) n'avait pas de marge pour la zone gestuelle iOS. Ajout de `paddingBottom:"env(safe-area-inset-bottom)"` (et variantes `calc(Npx + env(...))` pour préserver le padding existant) sur les 3 barres fixes en bas d'écran. `viewport-fit=cover` déjà présent dans `index.html` (prérequis pour que `env()` se résolve à une vraie valeur sur iPhone à encoche/barre gestuelle) — non modifié. Vérifiable seulement partiellement ici (le Browser pane n'émule pas un vrai iPhone à encoche, `env()` s'y résout à 0 — comportement correct et attendu, pas un bug de test).
>
> **3) « Sur ordinateur, le nom des sections est caché par le texte de version »** — bug de pile CSS (stacking context), pas juste un z-index mal choisi. La barre d'onglets (`zIndex:90`) était nichée dans un conteneur ancêtre `position:relative;zIndex:10` (le wrapper `maxWidth:900` du contenu) — un `position:fixed` descendant d'un ancêtre qui établit son propre contexte d'empilement (position + z-index non-auto) voit son z-index comparé **localement** dans ce contexte, pas au niveau global. Le pied de page version (`zIndex:50`, sans ce genre de wrapper) gagnait donc la comparaison réelle au niveau extérieur (50 > 10) malgré un z-index nominal de 90 sur la barre d'onglets. Aucun autre élément proche n'avait besoin de ce `zIndex:10` (aucun z-index 1-9 concurrent trouvé à proximité) — retiré purement et simplement. **Vérifié en Chrome** : `document.elementFromPoint()` au point de chevauchement retournait le texte du pied de page avant le correctif, l'onglet « Aujourd'hui » après — confirmé par capture d'écran (labels des 4 onglets bien visibles).
>
> **4) `.btn-press` généralisé** : les 21 boutons restants utilisant le style d'ombre pixel-art (`boxShadow:"Npx Npx 0 #0d0d0d"`) à travers App.jsx ont reçu la classe, en plus des 7 déjà faits en v2.2.0 — couvre notamment le composant `PBtn` partagé du portail parent (bénéficie à de nombreux boutons d'un coup).
>

## Architecture clé

```
App state:
  screen: "loading"|"setup"|"login"|"game"
  config: { players[], pin, tasks[], rewards[], updateFeedEntries[] }
  gameStates[]: { xp, coins, completed[], pending[], owned[], equipped{},
                  boughtRewards[], badges[], pin, avatar{} }
  view: "family" | playerIndex (number)
  parentMode: bool
  parentPinOpen: bool

Helpers:
  getLevel(xp) → { level, xpForNext, xpInLevel }
  getLevelTitle(xp, themeId) → { title, icon }
  getPlayerTheme(themeId) → theme object (couleurs, icônes, perso)
  displayName(player) → pseudo || name
  checkBadges(pState, player, dailyCount) → new badge IDs[]
  migrateGameState(gs) → gs with all new fields
  migrateSavedData(data) → data with migrations + changelog entries

Composants principaux:
  LoginScreen       — écran de sélection joueur/parent
  SetupWizard       — configuration initiale famille
  FamilyOverview    — vue "tout le monde"
  PlayerDashboard   — vue individuelle (XP, badges, tâches, shop)
  ParentPanel       — gestion tâches/récompenses/PIN/export
  RewardPopup       — popup après tâche complétée (XP + badges)
  AvatarCanvas      — rendu pixel-art personnage
  PinPad            — pavé PIN validation tâche/mode parent (in-game) — A UN BOUTON VALIDER
  PinDots           — indicateur 4 points PIN (login screen)
  PinKeypad         — clavier numérique (login screen) — PAS de bouton valider intégré
                      → le bouton VALIDER est ajouté dans le JSX parent selon le contexte
  MiniGame          — whack-a-mole au level-up
```

### Différence PinPad vs PinKeypad (important!)
- `PinPad` (ligne ~1231) : utilisé **in-game** pour valider tâche ou accéder au mode parent. **A son propre bouton VALIDER intégré.**
- `PinKeypad` (ligne ~2682) : utilisé sur l'**écran login**. Clavier uniquement, **pas de bouton VALIDER intégré** — le bouton est ajouté dans le JSX appelant (`mode==="pin"` et `mode==="parent"` dans `LoginScreen`).
