> **Audit (25 juillet, documentation seulement, aucun code touché) — transparence « gagné vs offert ».** Piège relevé par Common Sense Media chez Habitica : distinction pas claire entre récompense gagnée en jeu et achat en argent réel. Livre de Quêtes n'a aucun achat réel, mais l'item demandait de vérifier qu'aucune ambiguïté similaire n'existe entre "gagné avec ses pièces/son effort" et "offert par un parent/le boss/un frère-sœur". Relecture de tous les points de contact :
> - **Fil de famille** (`pushFeed`, `App.jsx`) — seulement 3 types d'entrées possibles : `chat` (message posté), `gift` (don de pièces entre enfants, texte explicite « X a donné Y pièces à Z 💛 » ou « a envoyé »), `boss` (victoire collective, texte explicite « La famille a VAINCU... pour tout le monde! »). Les complétions de tâches individuelles et les achats en boutique ne sont JAMAIS publiés au fil — donc aucune confusion possible entre "gagné" et "offert" au niveau du fil, puisque le seul mouvement de pièces personne-à-personne qui y apparaît est déjà étiqueté sans ambiguïté.
> - **`RewardPopup`** (récompense de tâche complétée, `popups.jsx`) — titre « ⚡ QUÊTE [verbe] VALIDÉE! » + nom de la tâche + XP/pièces : toujours lié explicitement à LA tâche que l'enfant vient de faire = clairement gagné par son propre effort.
> - **Popup victoire de boss** (`bossWin`, `App.jsx` ~6500) — « Vous avez vaincu [Boss] **en équipe**! 💪 » : cadrage explicite d'effort collectif, pas un achat ni un don individuel.
> - **Toast d'achat boutique** (`handleBuy`) — « 🎉 [emoji] [nom] acheté! » : verbe "acheté" explicite, distinct du verbe "gagné"/"validé" des récompenses de tâche.
> - **`handleForceComplete`** (override parent, portail) — cas à part : le parent peut marquer une tâche complétée pour un enfant depuis le portail (outil de rattrapage administratif, ex. tâche faite hors-ligne). Le résultat (XP/pièces/`completed[]`) est identique en tout point à une auto-complétion approuvée normalement — aucun marqueur ne distingue les deux après coup. **Jugé volontairement HORS du périmètre de cet audit** : ce n'est pas la même catégorie de risque que le piège Habitica (achat réel déguisé en récompense de jeu) — c'est un outil de correction de données utilisé PAR le parent, jamais présenté à l'enfant comme un événement distinct, et le comportement actuel (traiter la tâche comme faite, point) est probablement le comportement voulu plutôt qu'un bug de transparence.
>
> **Conclusion : aucune ambiguïté "gagné vs offert" trouvée, aucun changement de code nécessaire.** Tous les textes déjà en place distinguent clairement la source (tâche complétée, don personne-à-personne, victoire d'équipe, achat) par leur verbe et leur cadrage.

> **Audit (25 juillet, documentation seulement, aucun code touché) — `SetupWizard` (5 étapes) contre le principe d'onboarding de Finch ("une grande carte, une seule décision à la fois, pas de formulaire dense").** Demandé explicitement en mode audit-seulement — pas de restructuration, décision laissée à Gen. Relecture des 5 étapes (`src/setupwizard.jsx`) :
> - **Étape 0 (Mode)** — ✅ respecte bien le principe : 2 grandes cartes cliquables (Rituel/Semaine), une seule décision. Léger bundling secondaire : choisir "Rituel" fait apparaître un 2e champ (heure de fin) sur le même écran plutôt que sur une étape séparée — mineur, le champ est clairement subordonné au choix principal.
> - **Étape 1 (Joueurs)** — 🔴 la plus éloignée du principe. Chaque carte-joueur empile 4 décisions différentes (nom, pseudo, couleur, thème personnel) et TOUTES les cartes-joueurs sont visibles/actives simultanément sur un seul écran (jusqu'à 6 chez nous : 4 vraies + marge) — donc jusqu'à ~16-24 décisions visibles en même temps sur cet écran, l'inverse du modèle Finch "une carte, une décision".
> - **Étape 2 (Tâches)** — 🔴 également éloignée, mais pour une raison structurelle différente : c'est l'écran qui construit le vrai planning (qui fait quoi, quel jour/heure), donc chaque tâche assignée porte intrinsèquement plusieurs décisions (joueur(s), jour(s) ou heure, dupliquer/retirer) en layout 2 colonnes catalogue+assignées. Compresser à "une décision à la fois" ici demanderait probablement une refonte multi-écrans (1 tâche = 1 sous-étape), pas un simple ajustement.
> - **Étape 3 (Récompenses)** — 🟡 plus proche : chaque ligne est une seule micro-décision répétée (cocher/décocher une récompense), le pattern est cohérent même si plusieurs lignes sont visibles ensemble — modèle "liste de choix simples", moins dense que 1/2.
> - **Étape 4 (PIN)** — ✅ respecte pleinement le principe : une carte, une décision (saisir un code à 4 chiffres), texte explicatif clair, rien d'autre sur l'écran.
>
> **Conclusion** : sur 5 étapes, 2 respectent déjà bien le principe (Mode, PIN), 1 est proche (Récompenses), 2 sont nettement plus denses que le modèle Finch (Joueurs, Tâches) — mais ces 2 dernières portent aussi la plus grosse charge fonctionnelle du wizard (identité de 4 enfants + planning complet), donc les compresser demanderait un vrai découpage en sous-écrans plutôt qu'un ajustement de style. Aucune restructuration faite — décision laissée à Gen.

> **Cause trouvée par lecture de code** (`remotePush`, `App.jsx`) : le push cloud est débounced via un seul timer partagé (`_pushTimer`, `setTimeout(...,1500)`) — quand ce timer se déclenche enfin, son callback fait DEUX appels réseau séquentiels (GET cloud + fusion + PUT), ce qui peut prendre plusieurs centaines de ms à quelques secondes sur un réseau réel. Si une NOUVELLE action (ex: ajouter une tâche) survient PENDANT ce vol, `save()` écrit correctement la version fraîche dans `localStorage` tout de suite — mais `clearTimeout(_pushTimer)` ne peut plus annuler le callback déjà démarré. Quand ce vieux callback termine enfin son vol, il **écrasait purement et simplement `localStorage`** avec `toWrite` — une version bâtie sur une fermeture PLUS VIEILLE que l'action entre-temps — faisant disparaître ce qui venait tout juste d'être ajouté. La boucle de sync périodique (25s) ou le prochain rendu pouvait alors relire cette version régressée et "effacer" la tâche à l'écran, alors même que l'enfant avait vu le toast de confirmation.
>
> **Fix** : même principe de « fusion avant écriture » déjà appliqué à l'écriture cloud (commentaire existant juste au-dessus) — appliqué maintenant aussi à l'écriture locale finale, dans les 2 branches de `remotePush` (API REST + Supabase) : juste avant le dernier `localStorage.setItem`, on relit `localStorage` une dernière fois et on fusionne `toWrite` par-dessus via `mergeFamily` (union non-destructive, comme partout ailleurs dans le code) au lieu d'écraser bêtement. Résultat : peu importe l'ordre d'arrivée des callbacks concurrents, `localStorage` ne peut plus jamais RÉGRESSER — seulement converger. **Vérifié** : `npm run build` propre. Vérification en direct de la race exacte non concluante cette passe (fenêtre de course de quelques centaines de ms, difficile à provoquer de façon fiable en session solo) — confiance basée sur (1) lecture attentive du mécanisme exact reproduisant le symptôme rapporté, (2) le correctif réutilise mot pour mot le patron déjà validé et en prod pour l'écriture cloud (juste au-dessus dans le même fichier), (3) smoke-test du chemin normal (ajout de tâche par un enfant) en Chrome confirmant zéro régression — tâche apparaît immédiatement, zéro erreur console. **Pas fait dans cette passe** (hors scope du bug signalé, décision documentée) : dédoublonnage des 3 assignations `tr04` déjà dupliquées en prod pour Antoine Emery (aucune écriture directe faite sur la prod depuis cette routine, conformément à la consigne) — inoffensif (juste une tâche qui compte 3x dans sa liste au lieu d'1x), à nettoyer manuellement si Gen le souhaite, ou lors d'une prochaine migration ponctuelle dédiée si le motif se reproduit.

> **v1.95.0 (22 juillet, poussé, session nocturne autonome) — Lot 5 #23 (partiel) : `React.memo` sur `FamilyOverview`/`ParentPanel` + callbacks stabilisés.** En creusant avant de coder : `React.memo` seul n'aurait servi à RIEN, parce que `App()` passait à ces deux composants (et à `PlayerDashboard`) des tableaux `allTasks`/`allRewards` recréés (`[...TASK_CATALOG, ...]`) et des callbacks inline (`onClick={()=>...}`) à CHAQUE render — des références toujours "différentes" pour la comparaison superficielle de `memo`, qui aurait donc re-render ces enfants de toute façon (memo devient un no-op silencieux, pas juste inefficace). **Fix en 3 parties** : (1) `allTasks`/`allRewards` passés en `useMemo` (dépendent de `config?.customTasks`/`config?.customRewards`, stables sinon) — bénéficie aux 3 composants d'un coup; (2) les ~8 callbacks inline passés à `FamilyOverview` (`onSelectPlayer`, `canOpen`, `onLike`, `onPostChat`) et `ParentPanel` (`onClose`, `onExitParent`, `onReset`, `onSetup`) sont maintenant des `useCallback` nommés (les handlers `handleXxx` sous-jacents étaient déjà presque tous `useCallback` depuis un moment — seule la couche de "currying" avec `view`/`parentMode`/`sessionPlayer` ne l'était pas); (3) `FamilyOverview`/`ParentPanel` enveloppés dans `memo(...)`. **Bug réel trouvé et corrigé avant de pousser** : la première tentative plaçait ces nouveaux `useCallback` juste avant le `return (` du JSX principal de `App()` — mais `App()` a plusieurs `return` précoces AVANT ce point (`screen==="loading"/"setup"/"login"`), donc ces hooks n'étaient PAS appelés à chaque render → violation des Rules of Hooks (« Rendered more hooks than during the previous render »), écran noir/crash React confirmé en Chrome. Déplacés avant tous les `return` précoces (juste après le `useMemo` de `dayPct`), avec chaînage optionnel (`config?.players`) puisque `config` peut être `null` à ce stade du render (écrans loading/setup). **`PlayerDashboard` volontairement PAS touché cette passe** : il reçoit ~24 callbacks inline différents (contre 4 pour chacun des deux autres) — les convertir tous d'un coup dans une seule passe autonome nocturne aurait été le genre de gros diff risqué que la routine doit éviter; à faire dans un futur incrément séparé, idéalement en même temps que le découpage de fichier du #24 (qui forcera de toute façon un passage explicite des props). **Vérifié en Chrome** (dev server + `localStorage` seedé, 2 joueurs test) : tout le parcours parent rejoué en direct après le fix — login Parent (PIN), vue Famille, post au fil de famille, like ❤️, ouverture fiche Profil, clic "Voir mes quêtes" (navigation vers le dashboard d'un enfant), ouverture/fermeture du portail parent (✕ puis réouverture), sortie du mode parent, déconnexion complète → retour à l'écran de connexion — aucun crash, aucune régression visuelle. `npm run build` propre (mêmes 2 warnings préexistants bénins), `git status`/`git fetch` vérifiés propres avant de committer (aucune collision avec une autre session). **Reste du Lot 5** : #23 fini pour `PlayerDashboard` (voir ci-dessus), #24 (découpage progressif d'App.jsx), #25 (décision service worker/offline avec Gen — nécessite son avis, pas tranchable seul). **Prochaine étape suggérée** : soit finir #23 sur `PlayerDashboard`, soit commencer un tout petit premier incrément de #24 (extraire un module vraiment autonome, sans état partagé, comme point de départ prudent).

> **v1.94.0 (21 juillet, poussé, session nocturne autonome) — Lot 5 #22 : isoler le tick d'horloge.** Root-cause confirmée : `App()` (le composant racine, ~7000 lignes de JSX en-dessous) avait un `setInterval(...,1000)` qui mettait à jour un état `now` — donc TOUT l'arbre (PlayerDashboard, FamilyOverview, ParentPanel, etc.) re-render chaque seconde, même si l'horloge affichée (`{H}:{M}`) n'a même pas besoin de précision à la seconde (la variable `S` était calculée puis jamais utilisée dans le JSX — l'affichage n'a jamais montré les secondes). **Fix en 2 parties** : (1) nouveau petit composant `HeaderClock` (même patron que `Countdown`/`InlineRitualTimer` déjà existants — état + interval **locaux**, isolés) qui gère lui-même son tick de 1s pour l'affichage H:M du header, sans jamais faire re-render `App()`; (2) le tick restant dans `App()` (qui alimente la barre de progression du jour, le compte à rebours de rituel, l'indicateur de synchro cloud — aucun de ces éléments n'a besoin d'une précision à la seconde) est passé de 1000ms à 30000ms. **Mesuré en Chrome** (dev server local + `console.count` temporaire sur le rendu de `App()`, retiré avant le commit) : avant un rendu ~1×/seconde attendu par construction (l'ancien code), après le fix seulement ~4 rendus observés sur une fenêtre de 30s (le tick `now` à 30s + le tick de synchro cloud à 25s + probablement 1-2 effets ponctuels) — la cascade "chaque seconde" est confirmée disparue. `npm run build` propre (mêmes 2 warnings préexistants bénins), `git status` vérifié propre avant et après (aucune collision). **Reste du Lot 5** : #23 (`React.memo` sur PlayerDashboard/FamilyOverview/ParentPanel + `useMemo` sur les listes lourdes — bénéficiera encore plus du fix ci-dessus une fois en place), #24 (découpage progressif d'App.jsx en plusieurs fichiers), #25 (décision service worker/offline avec Gen). **Prochaine étape suggérée : #23**, qui est la suite naturelle de ce fix (moins de re-renders déclenchés + composants qui ignorent les re-renders inutiles = double gain).

## Architecture clé

```
App state:
  screen: "loading"|"setup"|"login"|"game"
  config: { players[], pin, tasks[], rewards[], updateFeedEntries[] }
  gameStates[]: { xp, coins, completed[], pending[], owned[], equipped{},
                  boughtRewards[], badges[], pin, avatar{} }
  view: "family" | playerIndex (number)
  parentMode: bool
  parentPinOpen: bool

Helpers:
  getLevel(xp) → { level, xpForNext, xpInLevel }
  getLevelTitle(xp, themeId) → { title, icon }
  getPlayerTheme(themeId) → theme object (couleurs, icônes, perso)
  displayName(player) → pseudo || name
  checkBadges(pState, player, dailyCount) → new badge IDs[]
  migrateGameState(gs) → gs with all new fields
  migrateSavedData(data) → data with migrations + changelog entries

Composants principaux:
  LoginScreen       — écran de sélection joueur/parent
  SetupWizard       — configuration initiale famille
  FamilyOverview    — vue "tout le monde"
  PlayerDashboard   — vue individuelle (XP, badges, tâches, shop)
  ParentPanel       — gestion tâches/récompenses/PIN/export
  RewardPopup       — popup après tâche complétée (XP + badges)
  AvatarCanvas      — rendu pixel-art personnage
  PinPad            — pavé PIN validation tâche/mode parent (in-game) — A UN BOUTON VALIDER
  PinDots           — indicateur 4 points PIN (login screen)
  PinKeypad         — clavier numérique (login screen) — PAS de bouton valider intégré
                      → le bouton VALIDER est ajouté dans le JSX parent selon le contexte
  MiniGame          — whack-a-mole au level-up
```

### Différence PinPad vs PinKeypad (important!)
- `PinPad` (ligne ~1231) : utilisé **in-game** pour valider tâche ou accéder au mode parent. **A son propre bouton VALIDER intégré.**
- `PinKeypad` (ligne ~2682) : utilisé sur l'**écran login**. Clavier uniquement, **pas de bouton VALIDER intégré** — le bouton est ajouté dans le JSX appelant (`mode==="pin"` et `mode==="parent"` dans `LoginScreen`).
